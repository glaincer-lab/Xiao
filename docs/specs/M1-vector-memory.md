## 1. 目的与范围

为什么存在：M1 检索注入现状是「全量收集 → 规则过滤（sandbox/expired/任务态）→ 全量注入」（retrieval.py 的 build_injection → render_injection）。记忆随使用增长后，注入 token 膨胀、且无关记忆混入污染上下文。改为「向量语义召回 Top-K（四因子排序）」，既省 token 又更准——这是「伙伴记得住」的前提。

存储治理：按「短期全量 / 长期向量 / 超长期遗忘」三层时间窗口 + 容量上限治理（老板定稿：全量 2 年、向量 10 年、超长期失效标记、记忆预算默认 300MB、占用超限弹窗确认、绝不静默扩容）。

明确不做：
- 知识图谱（Graphiti/Zep 那类，过重：需实体识别 + 关系建模 + 图存储 + 图查询 + 冲突消解，与「零依赖、开箱即用」冲突；且 P0 关系规模小、用不上。缓解：向量条目 meta.kind 打 person/milestone 标签，P0 检索「标签优先 + 向量兜底」）
- 云端向量库（本地优先，数据不上云）
- LLM 自动管理分页（MemGPT 那类，过重；首版用固定规则）
- 心理标签（人格宪法红线）

## 3. 数据结构（字段级）

### 3.1 向量条目（长期层，进向量库）

sqlite-vec 表 memories 字段：
- id：唯一 id（hex12）
- text：摘要/记忆内容（检索返回的正文）
- embedding：f32[512]（bge-small-zh-v1.5 向量）
- meta：kind（semantic/episodic/milestone/person）、scope、effective_at、source、status（active/invalidated）、confidence、importance（检索加权用，P0 恒高）
- ts：时间戳（近因加权）

### 3.2 三层记忆（水桶机方案，老板定稿）

| 层 | 窗口 | 内容 | 存储形式 |
|---|---|---|---|
| 短期全量 | 最近 730 天（2 年） | 对话全文 + 上下文快照 | 原文件（JSON） |
| 长期向量 | 第 1 天 ~ 第 10 年 | 摘要 + 向量（相对细节） | 向量库（摘要+向量） |
| 超长期遗忘 | 第 10 年之后 | 仅保留 P0 核心（人设/亲友/成长里程碑）+ 失效摘要指针 | P0 资产 + 失效指针 |

> 注：向量从第 1 天起持续积累；全文只保留最近 730 天，第 731 天起清理全文、只留向量。

### 3.3 与 M1 五要素 schema 的关系

向量条目是 M1 画像条目 + M6 共同记忆的「检索投影」，不是新的真源：真源仍是 M1 画像存储 + GrowthStore。向量库是派生索引，可由真源重建（导出/迁移时可选不打包向量，靠真源重建）。

## 4. 状态机 / 流程

### 4.1 写入（后台异步巩固流水线，复用巩固层）
对话结束 → 后台异步 → 原文提炼成**事件摘要** → 再提炼成**画像/事实** → P0 级再抽象（多级巩固，类比 Letta sleep-time）。新记忆条目（画像/共同记忆/里程碑）→ 摘要化（复用 consolidate，已摘要则跳过）→ encode(摘要) → upsert 向量库（id 幂等）。

### 4.2 检索（注入时，四因子混合排序）
user_request → encode(query) → sqlite-vec 相似度召回候选 → **四因子加权排序** → 取 Top-K（K=8 可调）→ 过滤 sandbox/expired/invalidated → render_injection。

四因子（默认等权各 25%，权重可配置）：
- ① 语义向量：query 与记忆 embedding 的 cosine 相似度
- ② 关键词：query 与记忆 text 的公共词/字重叠度（首版简单重叠计分，不上重型 BM25/倒排）
- ③ 时间近因：记忆 ts 距今越近分越高
- ④ 重要度：meta.importance + P0 标签恒高加权

### 4.3 记忆生命周期（三层时间窗口 + 失效标记，后台触发式）

- 短期全量（0~730 天）：对话全文保留；第 731 天起，全文清理、只留向量。
- 长期向量（0~3650 天）：每天对话提炼向量持续积累；检索走四因子 Top-K 召回。
- 超长期遗忘（3650 天后）：向量条目按容量上限清理，**采用「失效标记 + 摘要指针」而非物理删除**——status 置 invalidated、清空 embedding 释放空间、text 替换为一句摘要指针（可回溯）；最低保留最近 1 个单元（单元=天），单单元超限整体保留不切碎。
- **P0（共同记忆 + 成长三轨）永不失效**：不进任何自动清理/失效标记，仅用户手动 forget 真删。
- 存储预算默认 300MB（记忆流水原文 + 向量合计）：占用达到 **80% 弹提醒（可暂缓）/ 95% 弹强提示**，由用户选择「清理旧记忆 / 提升空间 / 暂不处理」，**绝不静默扩容、绝不静默删除**。

### 4.4 异常路径
| 异常 | 处理 |
|---|---|
| embedding 模型缺失/加载失败 | 降级全量注入（回退现状行为），记结构化日志 |
| sqlite-vec 不可用 | 降级 numpy 暴力检索（零依赖兜底） |
| 向量库损坏 | 重建空库，靠真源重新向量化 |
| 清理中并发写 | 加锁，清理与写入互斥 |

## 5. 规则与话术（写死区）

| 规则 | 默认值 | 可调 |
|---|---|---|
| 短期全量窗口 | 730 天（2 年） | 是 |
| 长期向量窗口 | 3650 天（10 年） | 是 |
| 存储总预算（记忆流水+向量合计） | 300 MB | 是 |
| 向量召回 Top-K | 8 | 是 |
| 检索因子 | 语义向量 + 关键词 + 近因 + 重要度，等权各 25% | 是 |
| embedding 维度 | 512（bge-small-zh-v1.5） | 否 |
| 最低一次 | 至少保留最近 1 个完整单元；单单元超限整体保留 | 否 |
| 超长期清理方式 | 失效标记 + 摘要指针（非物理删除） | 否 |
| 存储满提示阈值 | 80%（提醒）/ 95%（强提示） | 是 |

铁则：共同记忆 + 成长三轨（P0）**永不失效、不进任何容量自动清理**，仅用户手动删（forget，物理真删）。

设置引导：settings_schema 加「存储」组，给「存储预算」档位（默认 300MB，可调 100MB / 500MB / 2GB / 自定义）。**存储占用达到阈值（80%/95%）时直接弹窗提醒用户**（「记忆存储已用 X%，是否清理旧记忆或提升空间？」），经用户确认后执行设置/清理，**绝不静默自动扩容或删除**。审计、路由两类日志从简：各设一个小容量上限，不纳入 300MB 精细预算管理。

## 6. 模块间接口（事件契约）

本模块不新增事件、不改 EVENT_TYPES 白名单：向量检索是 M1 retrieval.py 内部增强（build_injection 内部改四因子向量召回），容量清理是 DataTrack/审计/路由各自的内部后台任务，均不产生跨模块事件。跨模块交互复用现有事件（memory.profile_updated 等）。

## 7. 验收断言

- 召回相关性：给定 query，Top-K 含语义相关记忆（非仅关键词命中）。
- 四因子排序：语义向量 + 关键词 + 近因 + 重要度四因子参与排序，权重可配置。
- 降级兜底：embedding 不可用 → 自动降级全量注入，功能不中断；sqlite-vec 不可用 → numpy 暴力检索。
- 容量清理（失效标记）：超限 → 失效到回上限；最低保留最近 1 个单元；不切碎单元（单 run/单天整体失效）；失效条目 embedding 清空、保留摘要指针可回溯。
- 共同记忆不可自动失效：容量清理/失效标记不触碰 growth.json 三轨（断言清理前后三轨计数与 status 不变）。
- 存储满弹窗：占用达 80%/95% 阈值时触发弹窗，用户确认后才清理/扩容，绝不静默。
- 可重建：删向量库后，靠真源（画像 + GrowthStore）能重建索引。
- 迁移：向量库随 9 类资产导出，或标记「可重建」不打包（搁置，见 §8 问题 2）。
- 链接 EVAL.md 场景三（任务态数据轨直通）不因向量化而破坏。
